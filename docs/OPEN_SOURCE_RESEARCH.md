## 1. 候选仓库逐一评估

### 1.1 6tail/lunar-typescript ⭐ 采用（核心）

- **链接**：https://github.com/6tail/lunar-typescript
- **npm**：`lunar-typescript@1.8.6`
- **功能**：公历/农历互转、二十四节气（精确到秒）、干支、生肖、八字四柱、十神、藏干、纳音、大运、流年、小运、胎元、命宫、身宫、黄历宜忌、彭祖百忌、吉神方位、星宿、建除十二值星等。
- **技术栈**：纯 TypeScript，**零运行时依赖**，同时提供 ESM / CJS / `.d.ts`。
- **许可证**：MIT（LICENSE 文件已核对原文）。
- **维护情况**：父项目 `lunar-javascript` 1717 stars，2025-11 仍在更新；`lunar-typescript` 2025-11 发布 1.8.6。同作者维护 Python / Java / C# / PHP / Go 等 10+ 语言版本，算法口径一致，社区校验充分。
- **实际验证**（本地安装后运行）：
  - 四柱：`1990-01-01 12:00` → `己巳 丙子 丙寅 甲午`（年柱正确回退到 1989 年，因未过立春）
  - 立春换年：`2024-02-04 16:00` → 癸卯；`2024-02-04 17:00` → 甲辰（2024 年立春为 16:27，边界精确）
  - 节气定月：`2024-03-04` 月柱丙寅，`2024-03-06` 月柱丁卯（惊蛰 3/5 切换正确）
  - 晚子时流派：`setSect(1)` 日柱算次日、`setSect(2)` 日柱算当日，行为符合文档
  - 大运：男命阴年逆排、女命阳年顺排，`getYun(gender)` 顺逆正确
  - 闰月：2023 年闰二月，`Lunar.fromYmd(2023, -2, 15)` → 2023-04-05
  - 黄历：`getDayYi()` / `getDayJi()` 返回真实宜忌条目
- **采用模块**：`Solar`、`Lunar`、`LunarYear`、`EightChar`、`Yun`、`DaYun`、`LiuNian`、`JieQi`。
- **风险**：无（零依赖、MIT、无已知 CVE）。唯一注意点是其"宜忌"数据属于传统通书整理，不是天文计算结果，需在 UI 上标注数据性质。

## 3. 关键技术判断

### 3.1 为什么必须用库而不是自己写历法

自行实现二十四节气需要太阳黄经的精确计算（VSOP87 或截断级数），自行实现农历需要定朔定气 + 闰月规则。这类算法**错误是静默的**——算错了页面照样渲染，只是结果不对。`lunar-typescript` 的节气精确到秒，且被 10+ 语言版本交叉验证，自研没有收益只有风险。

### 3.2 为什么 `lunar-typescript` 的"宜忌"要标注

`getDayYi()` / `getDayJi()` 来自传统通书（《玉匣记》一系）的规则表，不是天文计算。它是"有据可查的传统文献整理"，但不是"可验证的天文事实"。因此本项目在黄历页把「节气/干支/农历」标为**算法计算**，把「宜忌」标为**传统通书整理**，两者视觉上区分。这是诚实性要求，不是免责话术。

### 3.3 流派差异的处理

`lunar-typescript` 的 `EightChar.setSect()` 控制晚子时（23:00–24:00）的日柱归属：

- `sect = 1`（默认）：晚子时日柱算**次日**
- `sect = 2`：晚子时日柱算**当日**

本项目把该选项暴露到 UI（"子时换日规则"），并在结果页显示当前采用的口径。年柱统一用**立春**换年（不用正月初一），月柱统一用**节气**定月（不用农历月）。这两个口径在命理界是主流共识，但仍在结果页的"计算依据"面板中写明。

### 3.4 真太阳时

`true-solar-time` 基于 Jean Meeus 天文算法，输出包含均时差（EOT）与经度时差两部分。实测乌鲁木齐（87.62°E）相对 120°E 标准经线偏移 **−129.84 分钟**，与经度差 32.38° × 4 min/° = 129.5 min 吻合，量级正确。

**默认关闭**，用户显式勾选才启用。原因：传统命理实践中"用北京时间直接排盘"仍是最普遍做法，擅自校正会让结果与用户用其他工具核对时不一致。开启时在结果页显示校正前后的具体时刻与偏移分钟数。

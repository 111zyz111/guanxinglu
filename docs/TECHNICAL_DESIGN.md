> 项目：观星录（中国传统命理文化体验与研究工具）

> 关联文档：[开源调研](./OPEN_SOURCE_RESEARCH.md) · [实施计划](./IMPLEMENTATION_PLAN.md) · [部署与合规](./DEPLOYMENT.md)

## 1. 设计原则

四条原则决定了后面所有的技术选择，冲突时按顺序取舍。

1. **计算与解释分离。** 历法、干支、五行计数由确定性算法产出；「这意味着什么」交给规则文本或语言模型。两者的边界在代码里是硬边界，不是注释里的君子协定。
2. **本地优先。** 出生信息默认不离开浏览器。只有用户主动点击「AI 解读」时，服务端才会收到排盘所需的字段，且服务端会重新计算，不信任客户端传来的四柱。
3. **口径可查。** 每一个可能因流派而异的判断（立春换年、节气定月、晚子时归日、真太阳时），都要在结果页写明采用了哪一种，并允许切换能切换的部分。
4. **不假装。** 没有配置 AI 就明说没有；时辰未知就留空时柱而不是补一个默认值；宜忌数据来自通书就标注「通书整理」；未验证的结论不写成已验证。

## 2. 技术栈与理由

| 层 | 选型 | 版本 | 为什么是它 |
| --- | --- | --- | --- |
| 框架 | Next.js（App Router） | 15.5 | 需要服务端渲染（黄历、命盘首屏）、服务端 API（AI 代理）、静态优化，一套东西全包；不需要另起后端 |
| UI | React + TypeScript | 19 / 5.7 | 类型是排盘数据结构的护栏。`BaziChart` 有 20 多个字段，没有类型几乎必然写错 |
| 样式 | Tailwind CSS + CSS 变量 | 3.4 | 变量层承载设计系统（色彩/字体/间距），Tailwind 负责排版；不引入组件库，避免风格被别人的审美绑架 |
| 历法 | lunar-typescript | 1.8.6 | 零运行时依赖、MIT、节气精确到秒、跨 10+ 语言版本互证。详见开源调研 |
| 真太阳时 | true-solar-time | 1.2.1 | MIT，基于 Meeus 均时差算法，附中国经纬度数据 |
| 校验 | Zod | 3.24 | 服务端 API 的入参校验，防止畸形请求打到排盘引擎 |
| 测试 | Vitest | 2.1 | 与 Vite/TS 同源，零配置跑 `.test.ts`，不需要 jsdom（核心是纯函数） |
| 存储 | localStorage | — | MVP 不需要账号。引入数据库的收益（跨设备）远小于成本（合规、运维、泄露风险） |

**刻意不引入的东西**：组件库（shadcn/antd）、动画库（Framer Motion）、图表库（ECharts/Recharts）、图标库、字体文件、状态管理库。

理由不是「极简主义」，而是：这一版的动画只有页面渐显与卦象逐爻出现，用 CSS keyframes 足够；五行图是 5 条横条，用 div 足够；图标 7 个，手写 SVG 比引入 300KB 的图标库更划算，也彻底避免图标授权问题。引入一个依赖就多一份许可证审查与升级负担。

## 4. 数据流

### 4.1 排盘（无服务端）

```
表单（客户端）
  └─ validateBirthInput()            前端先校验，给即时反馈
      └─ encodeBirthInput()          把输入编码进 URL 参数
          └─ /bazi/result?cal=solar&y=...
              └─ decodeBirthInput()  服务端解析（也是分享链接的入口）
                  └─ buildChart()    ← 唯一调用 lunar-typescript 的地方
                      ├─ 夏令时窗口判定
                      ├─ 真太阳时校正（可选）
                      ├─ EightChar → 四柱/十神/藏干/纳音/地势/旬空
                      ├─ 五行计数（本气）+ 五行加权（藏干）
                      ├─ 旺衰评估（得令/得地/得势 40-35-25）
                      ├─ 刑冲合会
                      └─ 大运/流年（getYun）
                          └─ <PillarTable> <WuXingChart> <DaYunTimeline>
```

命盘页是服务端组件：URL 即状态，刷新、分享、打印都天然可用，不需要额外状态管理。**代价**是 URL 里带着出生信息——这一点在记录页与设置页都明确提示了。

### 4.2 AI 解读（有服务端）

```
/bazi/reading?<同样参数>
  ├─ 服务端：buildChart() + buildRuleReading()   ← 不依赖 AI，先给确定性解读
  └─ 客户端：<AiReadingPanel>
       └─ POST /api/interpret { input, question? }
            ├─ Zod 校验入参（拒绝越界日期、超长问题）
            ├─ 内存限流（每 IP 每分钟 6 次）
            ├─ 服务端重新 buildChart()          ← 关键：不信任客户端四柱
            ├─ 拼装结构化 payload（四柱/五行/十神/大运/口径）
            └─ 调用模型（OpenAI 兼容 或 Anthropic）
                 └─ 返回纯文本，前端按小标题分段渲染
```

**为什么服务端重新排盘**：如果接受客户端传来的四柱，模型就可能被诱导「解读」一个不存在的命盘，而用户无法察觉。重新计算把「AI 只能解释、不能编造排盘」从提示词层面的要求，变成了架构层面的保证。

### 4.3 起卦（纯客户端）

铜钱摇卦的随机只用于决定每一爻的「背/字」，不参与卦辞生成。卦辞爻辞是静态数据，变卦由动爻位翻转确定性地算出。起卦过程（每一步算式）都记录下来，可展开核对。

## 5. 设计系统

### 5.1 色彩

定义在 `globals.css` 的 `:root`，以语义命名而非色值命名。

| 变量 | 值 | 用途 |
| --- | --- | --- |
| `--ink-900/800/700` | `#080b0f` / `#0c1016` / `#11171e` | 页面基底、面板层次 |
| `--dai` | `#16232e` | 黛青，次级面板与山影 |
| `--paper` / `--paper-deep` | `#f2ecdd` / `#e6ddc8` | 宣纸色，用于命盘、卦辞、黄历卡 |
| `--gold` / `--gold-soft` / `--gold-dim` | `#c2a15c` / `#e2cb96` / 28% 透明 | 细线、题头、强调 |
| `--cinnabar` | `#a8412f` | 印章、动爻、警示 |
| `--jade` | `#4f7f6b` | 生机、木行、正面状态 |
| `--text-primary/secondary/muted` | 米白三档 | 正文层级 |

五行色单独一组（`--wx-mu/huo/tu/jin/shui`），深色底与纸面各有一套墨色版本（`ELEMENT_COLOR` / `ELEMENT_INK`），保证同一种「木」在深底与纸面上都可读。

**克制规则**：金色只用于 1px 线条、小字标签与强调数字，不做大面积填充；朱砂只出现在印章、动爻、错误提示；全站没有渐变光晕背景。

### 5.2 字体

不打包任何字体文件（这是授权风险最高的一类资源）。标题走系统中文字体衬线栈（Songti SC → STSong → Source Han Serif → Noto Serif → SimSun），正文走系统黑体栈。代价是不同系统观感有差异，收益是零授权风险与零加载成本。

### 5.3 组件类

`globals.css` 里定义了少量语义类，避免每个页面重复堆 Tailwind：

`.panel`（暗色玻璃面板）· `.paper-surface`（宣纸面 + SVG 噪声纹理）· `.hairline`（细金线）· `.eyebrow`（拉开字距的题头）· `.seal`（印章）· `.btn-primary/ghost/quiet` · `.input` · `.seg`（分段控件）· `.chart-table` · `.vertical-rl`（竖排）

### 5.4 动效

只有三处：页面元素渐显（`fade-up`，60–320ms 阶梯延迟）、卦象逐爻出现（90ms 间隔）、铜钱翻转（摇卦时）。全部在 `prefers-reduced-motion: reduce` 下关闭。没有视差滚动、没有鼠标跟随光斑。

### 5.5 响应式

断点用 Tailwind 默认（sm 640 / md 768 / lg 1024）。关键处理：四柱表在手机上仍是 4 列（信息结构不能塌），字号从 2.6rem 降到 2.1rem；导航在 md 以下折叠为两列菜单；起卦区在窄屏改为纵向堆叠。

## 6. 关键实现决策

### 6.1 为什么时辰未知时用正午代入大运

`getYun()` 需要具体时刻才能算起运岁数。用 12:00 代入是误差最小的折中（距子时与亥时等距），并在 `warnings` 里明确写「实际起运年份可能相差数月」。另一种做法是不推大运——但那样用户会以为「没有大运」，而不是「暂时算不准」。

### 6.2 为什么旺衰用简化三要素模型

完整的旺衰判断要通根、透干、月令司权、合化、调候，各家权重不同，无法给出唯一答案。与其假装精确，不如给一个**可解释**的分数：得令 40 + 得地 35 + 得势 25，每一项都在 UI 上展开算式。`StrengthAssessment.method` 字段直接写明「这是简化模型，不同流派结论可能有差异」。

### 6.3 为什么五行给两套口径

「本气计数」（8 个字各算一个）直观、可核对，但低估了地支藏干的力量；「藏干加权」更接近实际，但权重本身是经验值。两个都展示，并在图上标明条形长度按加权、×n 是本气计数。用户能看到差异，而不是被一个数字说服。

### 6.4 黄历的数据分层

- 农历、干支、节气、星宿、值星：`lunar-typescript` 按天文算法与历法规则计算，可复算。
- 宜忌、彭祖百忌：该库内置的通书条目整理，属文献传承。

UI 上分开标注（黄历卡右上角「通书整理」+ 底部说明），因为这两类数据的可信度性质不同。

### 6.5 节气表的坑

`lunar-typescript` 的 `getJieQiTable()` 是按**农历年**组织的，单张表不包含本年末的冬至。最初直接查表导致 `getSolarTermsOfYear` 返回 23 个节气、12 月下旬「下一个节气」为空。修复方式是探测前一年 12 月、本年 1/6/12 月、次年 1 月共 5 张表，按公历年过滤去重。这个 bug 由测试发现（`almanac.test.ts` 断言 24 个节气与首尾项），已修复。

### 6.6 城市经纬度

`regions.ts` 是精简表（省会 + 主要城市），不是完整行政区划。用户可选「不填」，此时真太阳时不可启用（表单会禁用勾选框）。没有引入完整的行政区划库，因为那需要额外 2MB 数据与一份授权审查。

## 7. 错误与边界处理

| 场景 | 行为 |
| --- | --- |
| 日期不存在（2 月 30 日） | 表单即时提示，服务端 `buildChart` 抛错而不是返回空盘 |
| 农历闰月不匹配 | 提示「该年无闰X月」 |
| 年份越界（<1900 / >2100） | 表单与 Zod 双重拦截 |
| 时辰未知 | 三柱 + 明确警告，不补默认时柱 |
| 性别未填 | 不推大运 + 说明原因 |
| 真太阳时失败 | 回退标准时间 + 警告，不静默 |
| localStorage 不可用 | 全站功能可用，仅提示「不会保存」 |
| AI 未配置 | 返回 `configured: false`，页面显示配置说明，规则解读不受影响 |
| AI 超时/报错 | 显示错误 + 重试按钮，不吞掉错误 |
| 限流触发 | 429 + `Retry-After` |
| URL 参数缺失 | 命盘页显示「缺少出生信息」+ 去填写的入口 |

所有失败状态都有对应的 UI，没有空白页或无限 loading。

## 8. 隐私设计

- 出生信息只存在 `localStorage` 与 URL 参数里。
- 无账号、无埋点、无第三方分析、无广告 SDK、无 Cookie。
- AI 调用发送的字段：公历时刻、四柱、五行计数、十神、大运、计算口径、用户问题。**不发送**姓名（根本不收集）、IP 之外的身份信息。
- API Key 只在服务端 `process.env`，不写日志（错误信息里会截断服务商返回体到 160 字符，且不含请求头）。
- 历史记录可逐条删除 / 一键清空。
- 分享链接含出生参数，页面明确提示发送前确认。

## 9. 已知限制

1. **紫微斗数未实现。** 已登记（`iztro`，MIT），属独立排盘体系，接入会显著扩大范围。
2. **六爻纳甲未实现。** 起卦与卦象完整，但纳甲、六亲、世应体系未做，界面上没有假装做了。
3. **宜忌不可自定义。** 数据源固定，无法按流派切换。
4. **真太阳时不含历史时区数据库。** 中国 1949 年前的地方时、战时夏令时未处理，只有 1986–1991 全国夏令时窗口。
5. **城市表不完整。** 内置的是省会与主要城市的精简表（约 30 项），县级市需选最近的大城市；表单另提供「直接填经度」入口（东经为正、西经为负），可覆盖海外出生地。
6. **AI 输出无结构化校验。** 只做提示词约束，没有对模型输出做「是否编造了四柱」的自动检测。改进方向：让模型返回 JSON，逐字段与计算结果比对。
7. **无多语言。** 仅简体中文。繁体与英文需要独立的文案层。
